# 全国 配車・積み合わせ最適化ダッシュボード（delivery-consolidation-vrp）

東京都内の高密度な配送依頼にはVRP(配車最適化)の近似解を、地方拠点の低密度な配送にはシンプルな車格制約の計算を——**規模によって最適化の勘所が異なる**という前提を切り分けて設計した、配車・積み合わせシミュレーションダッシュボードです。

- **構成**: 単一`index.html`。ブラウザで開くだけで動作(Tailwind CDNのためネット接続が必要)
- **GitHub**: https://github.com/Logtk/delivery-consolidation-vrp
- **デモ**: https://logtk.github.io/delivery-consolidation-vrp/ (`main`へpushすれば数分後に自動反映)

## 背景と解決したい課題（Why）

配送先ごとに個別に車を手配していると、車の空きスペースや便数に無駄が出ます。一方で、この無駄をどう削減すべきかは、配送密度によって答えが変わります。東京都内のように1日十数件が密集するエリアでは、車格制限・付帯作業・時間指定といった現場の制約を踏まえた組み合わせ最適化(VRP)が効きますが、地方拠点のように1日数件しかないエリアでは、複雑な最適化をかけるコストに見合いません。この規模による最適化戦略の違いを最初から意識して設計に反映している点が、単に「まとめれば安くなる」という単純な主張との違いです。

## 機能概要とアーキテクチャ（What / How）

- **経営KPIカード(月間・全国)**: 全国の月間実績と積み合わせによる削減額・削減率を東京都内/地方拠点に分けて表示
- **表示日セレクタ(東京都内)**: 当月の営業日から1日を選び、その日の配送に絞って詳しく確認
- **車種別台数シフト比較グラフ**: 個別手配とまとめて積んだ場合で必要な車の台数・車種がどう変わるかを比較
- **現場制約インサイトログ**: 車のサイズ制限で便を分けた理由、エリアをまたいでまとめた理由などをテキストで説明
- **ルート別積載率詳細**: 便ごとの車種・件数・積み込み具合(重量・容積)・時間指定の有無を一覧表示
- **地方拠点サマリー**: 大阪・愛知・福岡・関東近郊・その他道府県の月間実績をまとめて表示
- **動的パラメーター**: 配送の時間帯の余裕、付帯作業(荷卸しの手伝い等)の所要時間をスライダーで変えると全国データがその場で再計算される

**計算ロジック**: 東京都内(1日15件想定)は車格制限・付帯作業・時間指定・重量/容積ダブルチェックを考慮した**貪欲法＋区部越境統合ヒューリスティックでVRP近似解**を算出。地方拠点は1日あたりの件数が少ないため、車のサイズ制限だけを考慮したシンプルな計算にしています。配送件数・運賃はすべて架空の目安値をもとにしたダミーデータです。

## 誰のためのツールか、どう自分たちに応用するか

**対象読者**: 自社便を持つ物流拠点・EC自社配送・部品即納便など、都市部の高密度配送と地方の低密度配送を併せ持つ配車担当。

**応用方法**: `index.html`内の`VEHICLES`(車格と運賃)、`AREAS`/`PREF_ZIP`(エリア定義)を自社の実際の車両ラインナップ・営業エリアに書き換えるだけで、同じ貪欲法+ヒューリスティックのロジックを自社の配送パターンに適用できます。東京都内のような高密度エリアが無く、全拠点が地方拠点型(1日数件)の場合は、都内向けのVRP近似ロジックはオーバースペックになるため、地方拠点サマリーの計算方式だけを使う方が適切です。

## 現在のステータスと直面している課題（Current Status & Technical Challenges）

東京都内・地方拠点それぞれのシミュレーションロジックは動作する状態まで実装が完了しています。実装にあたり意図的に選んだトレードオフと、未検証のまま残している技術的課題を明記します。

**構造的課題: ヒューリスティックの最適性が未検証**

現在の東京都内の最適化ロジックは、厳密な数理最適化(MILPやGoogle OR-ToolsのようなVRPソルバー)ではなく、貪欲法+区部越境統合ヒューリスティックによる近似解です。これはブラウザ上でパラメータを動かした瞬間に全国データを再計算できる速度を優先した、意図的なトレードオフです。ただし、このヒューリスティックが最適解からどれだけ乖離しているかは現時点では未検証で、次に取り組むべき技術的課題として認識しています。

**意図的なスコープ限定: 地方拠点のシンプル化**

地方拠点は1日あたりの件数が少ない(主要都市・近郊で1日平均3〜4件程度)ため、意図的に車格制約だけのシンプルな計算に留めています。これは手を抜いているのではなく、「規模に応じて適切な複雑度を選ぶ」という設計判断です。ただし、件数が将来的に増加した場合にどの閾値で都内と同じ最適化ロジックへ切り替えるべきかは、まだ設計していません。

## 今後の展望（Next Steps）

- 東京都内のヒューリスティック解を、Google OR-Tools等の実際のVRPソルバーによる厳密解(または高精度近似解)と比較検証し、性能を定量評価する。
- 地方拠点についても件数増加時に都内と同じロジックへ切り替える閾値設計。
- **現場制約インサイトログの高度化**: 現状はテンプレート文による説明ですが、配送条件の組み合わせが複雑になるほど、テンプレートでは表現しきれないケースが増えます。生成AIを使って、その日の制約の組み合わせから自然な説明文を都度生成する機能への発展は、強いエンジニアリングとの協業で検証したい領域です。

## データについて

配送先・手配実績・金額などの画面内のデータはすべてダミーデータです。実在の企業・取引・金額とは一切関係ありません。計算ロジックの詳細は`index.html`内のJavaScriptを参照してください。
